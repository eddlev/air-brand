01 — At a glance

A framework for AI work that keeps moving.

AIR is a prompt-based framework for structured AI work. It centers one active task and carries the project state needed to continue across sessions and compatible platforms.

Focused. Fluid. AIR.

One active task. Continuity without reconstruction. A project that is not confined to one provider.

Lead with framework in public language. Describe what AIR does conceptually as a governing layer. Describe how it operates in practice as a runtime. Never assume the reader already knows the word “runtime.”

The honest boundary

AIR runs through the host model. Its prompt-layer structure can organize work, surface uncertainty, preserve state, and apply explicit gates, but it does not create deterministic backend enforcement or guarantee correctness. Keep human judgment in the loop.

02 — Positioning & strategy

The work should survive the container.

Long AI projects usually fail in one of two directions: stay in one session long enough and the work becomes noisy; move to a new session or platform and the user has to reconstruct the project.

AIR is designed around a different assumption:

The container can change. The work keeps its state.

That idea is expressed through three brand states.

Focused

One active task at a time.

AIR keeps one task at the execution center while preserving the surrounding project state needed to perform it correctly.

Focused does not mean narrow. The active task is bounded; the wider project remains available as context, constraints, evidence, dependencies, approvals, and decisions.

State metaphor: solid.

Fluid

Continue, don't reconstruct.

AIR uses structured handoff state so work can continue in another session or compatible platform without manually rebuilding the project or teaching the new session how to proceed.

Fluid describes continuity of project state. It does not mean native model memory, automatic synchronization, or uninterrupted autonomous execution.

State metaphor: liquid.

AIR

The project is not confined to one provider.

AIR is designed to move with the work instead of requiring the work to stay inside a single multi-model workspace. The host platform can change while AIR's project structure remains coherent.

Compatibility still depends on the capabilities and constraints of the platform receiving AIR.

State metaphor: gas.

The promise

AI work, carried forward.

The three states are the public value system. Honesty, evidence, benchmarks, approval boundaries, and governance remain product principles beneath them.

03 — Personality & voice

Precise, honest, calm.

AIR sounds like a disciplined collaborator: exact without being cold, confident without hype.

The voice is:

  • precise
  • honest
  • disciplined
  • sovereign
  • calm
  • cooperative

AIR should sound confident because the structure is clear, not because the language is inflated.

Lexicon

Prefer

session · project state · active task · continue · handoff · platform · provider · compatible · supported · framework · governing layer · runtime · evidence · blocker · benchmark · approval · surface uncertainty · fail-closed

Use carefully

  • chat — only when literal conversation/chatbot meaning is intended. Prefer session when the subject is the work container.
  • model — use when actual host-model identity or behavior is the subject. Do not use it as shorthand for provider lock-in.
  • memory — AIR does not give the host model native memory. “Fluid memory” is customer language, not the technical mechanism.
  • seamless — avoid as an unqualified claim where a handoff action still occurs.

Avoid

revolutionary · magical · effortless · guaranteed · AI-powered · works everywhere · universal · validated correctness

Voice in practice

Instead of:
“Never start from scratch again.”

Use:
“The next session shouldn't be a restart.”

Instead of:
“Switch models without losing context.”

Use:
“Continue the project across sessions and compatible platforms.”

Instead of:
“A memory layer for every AI.”

Use:
“Structured project state, carried forward.”

05 — Logo system

The dot-in-frame mark.

The AIR mark does not change.

A brass rounded-square frame holds one ember dot.

The frame is AIR structure.
The dot is the active task.

The new state system expands the world around the mark; it does not redefine the mark itself.

A provider, platform, session, browser tab, or external workspace is an outer container. It may change around AIR. It is not what the canonical brass frame represents.

Rules

  • Keep the mark unchanged across Focused, Fluid, and AIR.
  • Do not morph it into a droplet, cloud, molecule, vapor, or phase icon.
  • Do not recolor, stretch, rotate, fill, or add decorative effects.
  • Ember remains reserved for the active point.
  • Use the surrounding composition — not logo distortion — to express state change.

06 — Color

One palette. Two equal themes.

AIR retains its warm-dark / warm-light system.

Foundation #1A1613
Canonical dark environment.

Paper #F5F4F2
Canonical light environment.

Brass #C9A227
AIR structure and identity.

Ember #FF5A1F
The active task / live point.

The states are not assigned their own colors. Focused is not “dark,” Fluid is not “blue,” and AIR is not “white.”

Dark mode

Foundation carries the environment. Brass geometry can take stronger visual prominence. Ember may have subtle local luminance, but glow is never required to understand meaning.

Light mode

Paper carries the environment. Dark ink handles primary text and critical labels. Brass remains structural. Ember remains focal.

Do not rely on glow, pale fades, or low-contrast gold text to make the state system work.

Theme parity rule

Light and dark are equivalent brand states. Neither is the secondary adaptation of the other.

State is communicated by:

  • form
  • spacing
  • density
  • hierarchy
  • containment
  • motion

Never by theme-dependent color alone.

07 — Typography

Space Grotesk & JetBrains Mono.

Space Grotesk carries display, headings, and body.

JetBrains Mono carries technical detail, captions, labels, state, and runtime notation.

No new typeface is required for Brand v2. Fluidity comes from composition and motion, not from switching to a softer or more decorative face.

08 — Graphic language

One mark. Three states. One identity.

The states-of-matter system is a creative grammar, not a literal science illustration.

Focused / solid

The composition becomes tighter and more stable.

Use:

  • defined brass frames
  • stronger alignment
  • denser grouping
  • compact spatial relationships
  • stable boundaries
  • one dominant ember focal point

The visual should feel like the work has taken shape.

Fluid / liquid

The composition shows continuity between containers.

Use:

  • repeated AIR state
  • readable connecting paths
  • controlled curves where they communicate transfer
  • containers that change while AIR state persists
  • movement with retained identity

Do not use droplets, decorative waves, watery blue, or shapeless blobs.

The visual should feel like the work can move without being rebuilt.

AIR / gas

The composition opens.

Use:

  • more negative space
  • multiple subtle outer containers
  • secondary provider/platform boundaries
  • quieter or partial outer frames
  • AIR structure remaining coherent between choices

Do not use clouds, vapor, smoke, or decorative particle fields as shorthand for AIR.

The visual should feel like the project is no longer owned by one container.

09 — Web & UI

Build the state into the interface.

The website and UI use the same mark, colors, typography, and spacing system in both light and dark modes.

The state grammar may appear in:

  • hero illustrations
  • feature transitions
  • handoff demonstrations
  • diagrams
  • cards
  • section density
  • interaction motion

Focused UI

Tighter grouping. Stable grids. Clear task center. One active ember signal.

Fluid UI

Show the same project state moving between sessions or compatible platforms. The transfer path must be understandable without animation.

AIR UI

Increase openness and reduce dependence on any single outer frame. Provider choices remain secondary to the AIR project state.

Accessibility

  • Respect prefers-reduced-motion.
  • Every animated explanation gets a static equivalent.
  • Keep focus indicators visible.
  • Do not rely on Ember alone for status.
  • In light mode, use dark text for critical labels; do not treat Brass or Ember as default body text colors.

10 — Motion

Motion is state transition, not decoration.

Focused: settle · align · lock
Fluid: carry · connect · continue
AIR: open · release the outer container · retain AIR structure

Ordinary interaction motion should remain short and purposeful, generally around 0.2–0.4s.

Do not use:

  • perpetual decorative loops
  • bouncing active points
  • fluid simulation for spectacle
  • animation that implies background activity AIR is not performing
  • transitions whose meaning disappears under reduced motion

Example technical post

AIR doesn't give a model magical memory.

It serializes the project state that matters — active task, decisions, constraints, evidence, approvals, and next step — so another session can continue from the work that already happened.

When generating AIR brand material:

  • Treat solid / liquid / gas as internal creative states, not product claims.
  • Use session where the subject is continuity.
  • Use platform/provider where the subject is vendor lock-in.
  • Use model only when the model itself is relevant.

14 — Governance and trust

Keep the existing governance substance.

AIR is prompt-based and host-model governed. It can structure the work, apply visible gates, surface uncertainty, and preserve project state, but it does not create deterministic backend enforcement.

Do not infer:

  • guaranteed correctness
  • universal compatibility
  • eliminated host drift
  • compliance
  • certification
  • safety
  • autonomous agency

from AIR's visible framework behavior alone.

16 — Do / don't

Do

  • Lead with the outcome.
  • Use Focused / Fluid / AIR as the value system.
  • Use session for the work container.
  • Keep one active ember point.
  • Use Brass for AIR structure.
  • Build every key visual for light and dark.
  • Preserve static meaning under reduced motion.
  • Explain the technical mechanism after the value is clear.
  • Keep the trust boundary honest.

Don't

  • Recolor or morph the mark.
  • Assign blue to Fluid or clouds to AIR.
  • Make dark mode the “real” brand.
  • Call AIR native model memory.
  • Claim universal platform support.
  • Turn Focused into tunnel vision.
  • Use “chat” when the real subject is a project session.
  • Use “model” when the real issue is provider lock-in.
  • Lead with governance mechanics before the user understands why they want AIR.
